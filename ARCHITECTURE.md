# VYUK — Architecture Map

**Read this first if you are about to edit this code.** It says what every
file owns, how data moves, where to change things, and which rules will
silently break the app if you violate them. Something misbehaving instead?
Go to [TROUBLESHOOTING.md](TROUBLESHOOTING.md). Want a machine to check
the basics for you? Run `python doctor.py` in this folder.

## What VYUK is

VYUK is a desktop voice assistant for Windows: a PySide6 app that holds a
real-time conversation with Google's Gemini Live API (`core/voice/live_client.py`),
remembers facts in a local SQLite database (`core/memory/memory.py`), and — the
point of the project — **controls the whole laptop**: it types,
clicks, runs commands, manages windows and files, and sees the screen,
through a registry of tools (`core/funnel/tools_registry.py` + `core/desktop/control.py`) that
Gemini calls as functions. Voice is the interface; laptop control is the job.

Run it (from inside this folder — the folder itself **must** be named
`voice_assistant`):

```bash
pip install -r requirements.txt
copy .env.example .env        # then put your GEMINI_API_KEY in it
python main.py
```

Python 3.10+. The API key can also be pasted into the app (first-run
onboarding or Settings); it is saved to `.env` by `core/config.py`.

## File map

Every file in the package, what it owns, and what it must never do.

### Root

| File | Owns | Must never | If it's wrong |
|---|---|---|---|
| `main.py` | Process entry point. Puts the package's **parent** folder on `sys.path`, creates the `QApplication`, shows `MainWindow`. | Contain app logic — it only launches. | App won't start, or `ModuleNotFoundError: voice_assistant`. |
| `doctor.py` | Stdlib-only health check (layout, syntax, deps, imports, tool registry, config, data, assets). | Import any third-party package at startup; crash — every check is wrapped. | You lose the fastest way to localise a broken install. |
| `requirements.txt` | The dependency list (google-genai, PySide6, sounddevice, numpy, pillow, opencv-headless, websockets, python-dotenv, psutil, pyperclip, pynput, playwright, plus the local brain's llama-cpp-python / kokoro-onnx / faster-whisper / pyttsx3, plus the Your-world pack's google-api-python-client / google-auth-oauthlib / google-auth-httplib2). | List a package nothing imports without a comment (pytesseract is there as a commented optional). | Fresh installs miss a runtime dep and fail far from the cause. |
| `.env.example` | Template for `.env`: `GEMINI_API_KEY`, `ASSISTANT_NAME`, `VOICE_NAME`, `MODEL_NAME`, sample rates. | Contain a real key. | Key leak; or confusing defaults. |
| `README.md` | User-facing overview, install steps, plugin how-to. | Promise features the code doesn't have. | Editors/users trust the wrong map. |
| `THIRD_PARTY_LICENSES.md` | Licence summary for the local-brain components (Qwen3, Whisper/faster-whisper/CTranslate2, llama.cpp, Kokoro, Piper, Ollama) with commercial-use notes. | Be treated as legal advice — it says so itself; be left behind when a default model/voice is swapped. | Commercial distribution on unverified licence assumptions. |
| `data/assistant.db` | Runtime SQLite file (created by `core/memory/memory.py`): tables `facts`, `conversation_logs`. | Be edited by hand or treated as source code. | Lost memory/history. Deleting it is safe — it is recreated empty. |
| `data/activity.log` | Runtime append-only tool log, one line per tool call: `timestamp \| tool \| success/error` (written by `ToolRegistry._log_activity` in `core/funnel/tools_registry.py`). | Be required for the app to work — logging is wrapped so it can never break a tool call. | You lose the first place to look when a tool misbehaves. |

## Data flow

### (a) The voice loop — mic → Gemini Live → speaker

```
 mic ──▶ core/voice/audio.py AudioManager._mic_callback (sounddevice thread)
           computes mic_level + spectrum_bands, pushes int16 PCM (16 kHz)
           into mic_queue ──▶ core/voice/live_client.py _send_audio_loop
           wraps chunks as audio/pcm;rate=16000 blobs ──▶ Gemini Live
                                                                │
 Gemini Live ◀── session (core/voice/live_client.py GeminiLiveSession.start)
           _receive_loop dispatches each response:
             • audio parts ──▶ on_audio_data callback
                               + audio_manager.enqueue_playback()
                               ──▶ _playback_callback ──▶ speakers (24 kHz)
             • text parts  ──▶ on_transcript("assistant", text)
                               + memory_store.log_message()
             • interrupted ──▶ audio_manager.interrupt_playback(), status LISTENING
             • turn_complete ──▶ status LISTENING
```

`gui/main_window.py` `BackendWorker` runs `live_session.start(audio_manager)`
on its own thread's asyncio loop and re-emits every callback as a Qt signal
(`BridgeSignals`), so widgets are only ever touched on the GUI thread.

### (b) A tool call — from Gemini's request to the result card

```
 Gemini decides to call a function
   ──▶ live_client._receive_loop: status THINKING
   ──▶ core/funnel/tools_registry.py  tools.execute(name, args)
         ──▶ handler: a _tool_* method in tools_handlers.py,
             OR a plain function in core/desktop/control.py,
             OR a plugin's run() from plugins/
         ──▶ ToolRegistry._log_activity() appends to data/activity.log
   ──▶ result dict {status, result} returned to Gemini as a FunctionResponse
   ──▶ live_client on_tool_call callback
   ──▶ BridgeSignals.tool_executed ──▶ MainWindow._on_tool(name, result)
   ──▶ _add_result_card() in the chat  +  earcons.done()
```

### (c) GUI state flow — status strings drive everything visual

```
 live_client._notify_status("LISTENING" | "SPEAKING" | "THINKING" |
                            "CONNECTING" | "ERROR: …" | "DISCONNECTED" |

   ──▶ BridgeSignals.status_changed ──▶ MainWindow._on_status(status)

```

### (d) Two brains, one loop

VYUK has two interchangeable engines behind `core/brain/brain.py`'s proxy, and
everything above this section applies to both: the **Gemini brain**
(`core/voice/live_client.py`, cloud, needs `GEMINI_API_KEY`) and the **local
brain** (`core/voice/local_client.py` — faster-whisper for ears, zero API
key). The GUI cannot tell them apart: identical callbacks, identical
status strings, identical tool registry — only the transport differs
(a websocket to Google vs a mic→STT→chat→TTS pipeline on the machine).
The engine is chosen per `start()` from `config.brain_engine`
(`BRAIN_ENGINE` in `.env`, switched from Settings), so flipping brains
never needs a code change.

Since v1.8 the local brain itself has two backends, chosen per
`start()` from `config.local_backend` (`LOCAL_BACKEND` in `.env`):
**builtin** (the default) runs the model in-process — llama-cpp-python
over a Qwen3-4B GGUF (the Balanced tier in `core/voice/local_assets.py`'s
`MODEL_TIERS`; a Qwen3-8B Quality tier is the upgrade option) that
`core/voice/local_assets.py` auto-downloads on first connect, Kokoro for
voice, and a JSON-block text protocol for tool calls (landmine 12) — while **ollama** (advanced) keeps the v1.7
design: an external Ollama server with native tool calls, Piper/SAPI
voice. Two honest asymmetries hold for both local backends: the local
brain's vision is **OCR-only** (since v2.7 `send_image_frame` runs the
frame's bytes through the same PIL + pytesseract read the
`ocr_screen` tool uses and the model answers from the text actually
read — a frame with no readable text still gets the honest "vision
needs Gemini" redirect) and its `client` is `None`, so the
end-of-session summary (Gemini-only) is skipped under it.

**The invisible brain (v2.7).** The default engine is now **local**
(`config.brain_engine` defaults to `"local"`; the cloud brain is the
opt-in), so a fresh install must work with zero decisions. When the
builtin backend's brain GGUF is still downloading, `core/brain/brain.py`
serves `core/voice/lite_client.py`'s `LiteLiveSession` instead: it starts
the pack download in the background (in the progressively-alive
order — ears, voice, brain), answers a deliberate set of intents
through the real tool registry, speaks through the real session's
TTS chain, and **auto-upgrades mid-session** to a full
`LocalLiveSession` the moment brain + ears are ready. Local speech
is also streamed since v2.7: `_speak()` splits multi-sentence
replies with `_split_sentences()` (abbreviation-guarded) and
synthesizes chunk-by-chunk with a one-sentence lookahead, so the
first sentence plays while the rest synthesize; barge-in drains the
pending chunk queue. Nothing about the first run asks the user a
question: every knob (engine, backend, tier, voices) still exists —
behind Settings, not in front of the first conversation.

## Invariants & landmines

These are real, paid for in debugging time. Do not "clean them up."

1. **The package folder must be named `voice_assistant`.** Every module
   imports `voice_assistant.*` (GUI files) or relative `core` imports, and
   `main.py` puts the folder's *parent* on `sys.path`. A folder named
   `voice-ai-assistant` (hyphens) is not importable — the app dies with
   `ModuleNotFoundError` before any window appears.
2. **The chat stylesheet rule is exactly one line:**
   `QWidget#chatContent { background: transparent; }` in `gui/style.py`,
   and the chat content widget in `_build_assistant_page()` gets an
   objectName and **no stylesheet of its own**. Adding child-combinator
   rules or a stylesheet on that widget previously painted the scroll
   area white and made VYUK's bubble invisible while everything still
   "compiled fine". Render-check GUI changes; don't trust compile checks.
3. **Chat bubbles and result cards use deterministic widths.**
   `ChatBubble.__init__` ends with
   `setFixedWidth(max(150, min(560, max(text_w, who_w, time_w) + 30)))`
   computed from `QFontMetrics`, and `_add_result_card()` does the same
   (`max(170, min(560, body_w + 30))`). A word-wrapping `QLabel` inside a
   stretchy row collapses to minimum width when a sibling toggles (the
   MiniEq did exactly this — bubbles rendered as thin slivers). Never
   replace this with stretch/minimum-size tricks.
4. **`ctypes.windll` only ever appears inside function bodies**
   (`core/funnel/tools_gate.py`, `core/funnel/tools_handlers.py`, `core/desktop/control.py`). At module level it would make
   the module un-importable on macOS/Linux — and `doctor.py`, CI, and
   any headless check import these modules on purpose.
5. **Destructive control tools are confirm-gated by design.**
   `core/desktop/control.py`: disk format/wipe patterns are refused even with
   confirmation (`_ALWAYS_REFUSE_PATTERNS`); destructive shell commands
   need `confirm=True` (`_CONFIRM_REQUIRED_PATTERNS`); `file_control`
   delete moves files to a sibling `_nova_trash/` folder, never permanent;
   `close_application` and `power_control` shutdown/restart require
   `confirm=True`. Removing a gate "because the model keeps forgetting"
   removes the product's safety story.
6. **Status strings are a protocol, not display text.** `live_client`
   emits `CONNECTING / LISTENING / SPEAKING / THINKING / ERROR: … /
   DISCONNECTED / MISSING_API_KEY`; `MainWindow._on_status()` and
   `OrbVisualizer._target_palette()` substring-match them. Renaming one
   silently desyncs the pill, the orb, and the thinking bubble.
7. **Tool names are a protocol too.** The registered names in
   `core/funnel/tools_registry.py` are the function names Gemini is given at connect.
   Renaming a tool renames the API — do it in the registration, the
   handler, and any docs together.
8. **QSettings identity is `QSettings("NovaAI", "VYUK")`** in
   `MainWindow.__init__`. Theme, orb style, sound settings, window
   geometry, and the `onboarded` flag live under it. Changing the
   org/app names orphans every user's saved settings.
9. **Saved theme names are validated against `THEMES`** in
   `_apply_saved_settings()` — if you rename a theme in
   `gui/visualizer.py`, old QSettings values fall back to "Indigo Teal".
   Add themes; don't rename them casually.
10. **`.env` is loaded at `core.config` import time**, and variables
    already in the process environment win over `.env` values
    (`load_env_file()` never overwrites). If a key "won't update",
    check the environment before blaming the file.
11. **The window imports `live_session` from `core.brain` — never from
    `core.live_client` directly.** `core/brain/brain.py`'s proxy is what makes
    the Gemini/local engine switch (`config.brain_engine`) reach the
    GUI: it re-reads the setting on every `start()` and delegates to
    the right engine. Importing `live_client.live_session` in the GUI
    silently hard-wires Gemini forever and the Settings brain toggle
    becomes a lie.
12. **Builtin tool calls use the JSON-block protocol — the GGUF chat
    template is NOT tool-aware.** The builtin backend has no native
    function calling: `_render_tool_protocol()` teaches the model to
    reply with only `{"tool": …, "arguments": …}` (parsed by
    `_extract_tool_call()`, which brace-matches, tolerantly parses, and
    **validates the name against the registry** before anything
    executes), and tool results return as `Tool result for <name>: …`
    user messages, because that is the only channel every chat
    template renders. Do not "simplify" this into regex extraction,
    do not feed results back as a fake `tool` role (many templates
    drop or mangle unknown roles), and do not skip the name check —
    it is the difference between a chat format and an execution hole.
    Three v1.9 companions live around the same protocol: brain models
    are chosen from `core/voice/local_assets.py`'s `MODEL_TIERS` (Balanced
    Qwen3-4B default, Quality Qwen3-8B upgrade — resolved by filename,
    never by a second config knob); `_ensure_llama()` attempts GPU
    offload (`n_gpu_layers=-1`) FIRST and falls back to CPU on any
    exception, in that order, so a CPU-wheel machine still loads; and
    `_strip_think()` removes leaked `<think>…</think>` reasoning
    blocks from spoken/stored replies (extraction still runs on the
    raw text) — deleting it makes VYUK read her chain-of-thought
    aloud whenever a reasoning model leaks it.
13. **`.part` files are sacred — they are resume state, not junk.**
    `core/voice/local_assets.py`'s `download_file()` streams into
    `dest + ".part"` and only `os.replace`s it into place when the
    transfer completes and verifies; an interrupted download's `.part`
    is exactly where the next attempt resumes (HTTP `Range`). Cleanup
    code, "tidy" scripts, storage janitors, or a zealous edit of
    `remove_offline_pack()` must never delete `.part` files outside
    the explicit, user-initiated pack removal — and even that removal
    stays scoped to `data/models/` + `data/voices/kokoro/` (see
    TROUBLESHOOTING §18). `model_ready()` / `kokoro_ready()`
    deliberately ignore `.part` files — don't "help" them count
    partials as ready either; a counted-as-ready partial is a corrupt
    model that llama.cpp loads and dies on.
14. **Scheduled routines still cannot inject `confirm=True` — and
    they fire through the window, in two modes.** Since v2.1 a
    routine record may carry a `schedule` (parsed by
    `planner.parse_schedule()`, interpreted by `planner.next_run()`,
    fired by `core/routine_scheduler.py`'s 20-second tick). Firing
    calls the **window's** callback: when a brain session is
    connected, the brain is asked to run the routine (so the user
    hears it happen, in chat and voice); when disconnected, the
    routine runs **headlessly** through `planner.run_routine()`.
    Neither mode changes the trust story: steps go through
    `tools.execute()` and the trust layer exactly as if typed, a
    refused step halts the routine, and there is no code path by
    which a schedule grants confirmation. The schedule field is also
    deliberately **not** in the `save_routine` tool schema
    (`core/funnel/tools_registry.py` declares only `name` + `actions`): the brain
    cannot invent schedules by voice — they are set in Settings or
    by editing `data/routines.json`, and `save_routine()` merely
    accepts/preserves the field for those callers. Firing history in
    `data/routine_state.json` is written **before** the callback
    runs; moving that write later re-opens double-firing after a
    crash.
15. **Lite-session lines are assistant-role only — learning must
    never see them.** The v2.7 lite session (`core/voice/lite_client.py`)
    speaks canned lines (the getting-ready line, the upgrade
    announcement). Everything it says goes through
    `on_transcript("assistant", …)`; its user transcripts are only
    ever the user's own typed/spoken words. The GUI's learning hook
    listens to user-role transcripts (with its own self-sent guard
    for window-injected sends), so lite's words can't be learned as
    user facts — as long as nobody "simplifies" lite into answering
    via a fake user turn or a `send_text` echo. Keep that boundary:
    the day lite's fallback line lands in the facts table as
    something "the user said", the memory is poisoned.

## Mind pack — plans & routines (`core/brain/planner.py`)

The Mind pack gives VYUK two kinds of multi-step memory, both stored as
plain, human-editable JSON in `data/`:

- **Plans** (`data/plans.json`): a goal plus ordered steps
  `{text, tool?, args?, status}` where status is `pending` / `done` /
  `skipped`. Tools: `create_plan`, `list_plans`, `get_plan`,
  `update_plan_step` (action `complete`/`skip`, zero-based step index),
  `delete_plan`. Creating or editing a plan executes **nothing** — a
  plan is a tracked checklist, not a script.
- **Routines** (`data/routines.json`): a name plus ordered actions
  `{tool, args}` (max 20), saved with `save_routine` — `actions` is a
  JSON **string**, because Gemini passes strings more reliably than
  nested objects. Tools: `save_routine`, `list_routines`,
  `run_routine`, `delete_routine`.

`run_routine` is the only Mind function that *does* anything, and it
deliberately does it the boring way: every action is dispatched through
`tools.execute()` (imported lazily inside the function — `core/funnel/tools_handlers_pack_core2.py`
imports `planner` at registration, so a top-level import would loop),
which means the activity log and `core/desktop/control.py`'s trust layer apply
unchanged. **Nothing is ever auto-confirmed**: if a step errors, names
an unregistered tool, tries to nest another routine, or comes back with
a trust-layer refusal ("Blocked by VYUK's trust layer…" / "Refused:…"),
the routine halts at that step and reports which step stopped and why.
Destructive routine steps therefore always need the user to confirm
that action separately, outside the routine.

Routines may also carry a **schedule** (v2.1): the record gains
`schedule` (a dict) and `schedule_text` (what the user typed), via
`planner.parse_schedule()` — `daily HH:MM`, `interval 45m` /
`interval 2h`, or `once YYYY-MM-DD HH:MM`. `planner.next_run()`
turns a schedule + last-run time into the next slot (a returned slot
in the past means "due now"). `core/routine_scheduler.py` ticks
every 20 s and fires due routines through the window's callback,
recording each firing in `data/routine_state.json` first (see
landmine 14). Schedules are set in Settings or by editing the JSON —
the `save_routine` **tool** schema has no schedule parameter, by
design.

Persistence rules for both files: a missing or corrupt file reads as
empty (never raises), and saves write a temp file then `os.replace` it
over the target, so a crash mid-save can't truncate the store.

## Noticing — watchers (`core/watchers.py`, v2.3)

The Watchers pack is how VYUK *notices* things instead of only
reacting: a `WatcherEngine` polls the machine every 30 s and emits
events — `battery_low` / `battery_critical` / `battery_full`,
`download_done`, `network_down` / `network_up`, `welcome_back`,
`disk_low`, `drive_connected` — each with a plain-language message
written to be spoken aloud.

The flow is deliberately one-directional:

```
 core/watchers.py WatcherEngine.tick()  (daemon thread)
   ──▶ on_event(kind, message) callback  (the window's bridge)
   ──▶ MainWindow posts the message in chat — always
   ──▶ and, when a brain session is connected, speaks it through
       the session (the brain says the line; no tool is invoked)
```

**The engine never executes tools and never speaks on its own.**
`core/watchers.py` has no reference to the tool registry, the
sessions, or the GUI; whether an event is spoken, which categories
are enabled (Settings → Presence → Notices toggles, applied
GUI-side), and what happens next are all window decisions. Every
watcher is a small state machine with a baseline or re-arm rule, so
an episode produces exactly one event — plus an engine-level 60 s
same-kind suppression as a backstop — and a probe that fails (no
battery on a desktop, psutil missing, no network route) silently
disables its watcher for that tick rather than erroring. Nothing is
persisted: baselines (existing downloads, connected drives) are
re-seeded from the live machine on every engine start, which is
exactly why files that were already in `~/Downloads` are never
announced.

## Your world — Google Calendar + Gmail (`core/google_services.py`, v2.4)

The Your World pack is how VYUK knows the user's *day*, not just their
machine: what's on the calendar, what's waiting in the inbox. Four
tools (`get_todays_schedule`, `get_upcoming_events`,
`get_unread_email`, `search_email`) wrap the module's plain functions
and are registered alongside the other packs — **brain-agnostic**:
Gemini calls them as native function declarations, the built-in local
brain calls them through its JSON-block protocol, Ollama through its
own conversion; nothing here knows or cares which brain is asking.

Access is deliberately narrow:

- **OAuth "Desktop app" flow.** `connect()` builds an
  `InstalledAppFlow` from a client config and calls
  `run_local_server(port=0)`: Google's consent page opens in the
  user's own browser, the code returns over a localhost redirect,
  and the credentials are saved to **`data/google_token.json`**
  (atomic tmp + `os.replace`, the same discipline as the other data
  stores). Access tokens are refreshed in `_load_credentials()` when
  expired and re-saved, so a connected account stays connected.
- **Read-only scopes, exactly two:** `gmail.readonly` and
  `calendar.readonly` (the `SCOPES` list). The token physically
  cannot send mail or modify events — read-only is enforced by
  Google, not by VYUK's good behaviour.
- **The client codes are the user's own — for now.** The OAuth client
  id/secret come from `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`
  (Settings → Your world, saved via `config.save_env_setting`, read
  as `config.google_client_id` / `google_client_secret`). Each user
  creates a free Google Cloud project, enables the Gmail + Calendar
  APIs, and makes a "Desktop app" client. The commercial path is a
  single **verified bundled client** shipped with the product (Google
  app verification for the restricted Gmail scope) so customers never
  see a Cloud console — until that exists, bring-your-own-codes is
  the honest route, and Settings says so.
- **Disconnect means disconnect:** `disconnect()` asks Google to
  revoke the token (best-effort POST to the revoke endpoint) and
  deletes `data/google_token.json`; every world tool then falls back
  to the single not-connected sentence until the user connects again.
- **Heads-ups data (v2.5):** `next_events()` returns upcoming events
  as structured dicts (`id` / `title` / `start` / `location` /
  `all_day`) — it powers the calendar heads-ups the window speaks
  shortly before an event starts. It is deliberately **not** a
  registered tool (the registry stays at 66), and it never raises:
  not connected, missing libraries, or any failure all come back as
  an empty list, which the window reads as "nothing to say".

Every google import is lazy (inside the function that needs it), so
the module — and therefore the tool registry and `doctor.py` —
imports cleanly on a machine where the Google libraries were never
installed; the four functions then simply report not-connected /
library-missing sentences instead of raising.

## She learns you — automatic preference memory (`core/memory/learning.py`, v2.6)

Everything above is VYUK knowing the user's *machine* and *day*.
This pack is how she learns the *user*: statements like "my name is
Aayur", "I love black coffee", "my sister's name is Diya" become
durable facts she still knows next week.

The flow:

```
 user's spoken/typed sentence
   ──▶ gui calls core/learning.learn_from_text(text)
   ──▶ extract_candidates(): deterministic regex patterns,
       pure — no model call, no store access
   ──▶ store.save_fact("learned", key, value) for each new/changed
       candidate (UNIQUE(category, key) upsert in core/memory/memory.py)
   ──▶ the window announces what stuck ("Noted — you like black
       coffee") and lists it on the Memory page ledger
   ──▶ from then on the fact rides get_memory_context_prompt()
       into every session/turn, like any hand-saved fact
```

Design rules, all deliberate:

- **Patterns, not a model.** Extraction is a fixed pattern set in
  `core/memory/learning.py` (name / preferred name / identity / likes /
  dislikes / habits / `my_<word>` attributes / `remember that …`
  notes). No extra model calls means it works identically — and
  offline — with both brains, and a learned fact is never a
  hallucination: it either matched a named pattern or it didn't
  happen.
- **Conservative by construction.** Questions teach nothing
  (sentences ending in "?" or opening with a question auxiliary are
  skipped); state/emotion stoplists keep "I'm happy" and "my phone
  is dead" out; "remember *to* X" is a task request, not a fact,
  and is ignored; a `remember that …` sentence is claimed by the
  note pattern as a whole. Likes / dislikes / habits are
  *multi-value*: each files under `likes_<slug>` /
  `dislikes_<slug>` / `habits_<slug>`, the slug being the value's
  first 3 words (lowercased alnum, ≤24 chars —
  `likes_black_coffee_in`), so distinct preferences coexist as
  separate rows instead of overwriting each other. The one
  accepted collision: a rephrase sharing those first 3 words
  ("black coffee in the morning" → "black coffee in the evening")
  lands on the same key and is treated as a correction of that
  like.
- **Corrections replace.** Re-stating a key with a new value
  upserts, leaving one row ("my name is Aayur" → "my name is Aayur
  Gattani"). Identical re-statements are no-ops.
- **Capped and reviewable.** Category `learned` is capped at
  `MAX_LEARNED` = 100 facts (replacements still work at the cap).
  Every learned fact is visible on the Memory page with a Forget
  button; forgetting is category-guarded (`forget_learned_fact`
  refuses ids that aren't `learned`), and learning itself can be
  switched off in Settings.
- **Keys are self-describing.** `display_for(key, value)` derives
  the second-person sentence ("your sister's name is Diya") from
  the stored key/value alone — the same derivation produces the
  announce line and the ledger text, so the two can never drift.

## Skills pack — the everyday gaps (`core/skills_plus.py`, v2.7)

An audit of the 66-tool registry (including the action vocabularies
inside the multi-action tools) found the classic control surface
already complete — clipboard write (`write_clipboard`), scroll and
drag (`mouse_control` / `cursor_control`), show-desktop
(`desktop_control`), workstation lock (`lock_screen`; *unlocking* is
impossible by Windows design, for VYUK and everyone). Nine genuine
gaps were added, taking the registry to **75 tools**:
`list_installed_apps`, `uninstall_app` (confirm-gated),
`print_file`, `read_pdf_text` (optional pypdf), `speak_text`
(system voice on demand), `eject_drive`, `set_focus_assist`,
`find_files`, and `monitor_control` (list + move-window). All are
plain string-returning functions with lazy/guarded platform imports,
registered through the module's own `register_all(registry)` —
the same pack pattern as `control_plus` and `cursor`. One audited
gap was deliberately NOT filled: reading the *focused document's*
text — `get_window_controls` / `click_element` (UI Automation)
already expose a window's named controls, and a raw document-text
dump is a different, heavier feature.


## System & Apps pack — deep Windows management (`core/skills_system.py`, v2.8)

Mega Skills 1 of 3. Fifteen tools taking the registry from **75 → 90**:
`winget_install` (search-then-install with the picked package named;
confirm-gated), `list_app_updates`, `winget_upgrade_all`
(confirm-gated), `list_startup_programs`, `set_startup_program`
(confirm-gated, HKCU-scope only — disabling MOVES a Run value into
`HKCU\Software\VYUK\DisabledStartup`, or a Startup-folder file into
`%APPDATA%\VYUK\DisabledStartup`, so enabling restores it exactly;
all-users entries refuse with an admin explanation), `list_services`,
`service_control` (confirm-gated; sc.exe error codes translated,
notably 5 = needs an administrator VYUK), `power_plans` (list/set,
set confirm-gated), `battery_health` (powercfg /batteryreport parsed
for design vs full-charge capacity + cycles; temp report deleted
after), `env_var` (user scope HKCU\Environment; set confirm-gated),
`registry_read` (READ-ONLY by design — this module contains no
registry-write tool), `disk_health` (Get-PhysicalDisk via
PowerShell), `clean_temp_files` (reports sizes first; confirm deletes
only files older than 7 days, locked files skipped and counted),
`largest_files`, and `find_duplicates` (size-group → 64 KB partial
hash → full sha256; reports only, never deletes). Same pack pattern
as `skills_plus`: plain string-returning functions, lazy/guarded
platform imports, honest non-Windows fallbacks, and the module's own
`register_all(registry)` — wired into `core/tools_handlers_pack_hands.py` by the parent (`_register_skills_tools`).
